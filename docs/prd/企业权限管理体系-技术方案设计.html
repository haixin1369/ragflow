RAGFlow 企业权限管理体系 · 技术方案设计

版本：v0.1（待评审） 日期：2026-11-21 依据：《企业权限管理体系-功能需求文档》v0.3（已定稿） 技术栈：Go 后端（internal/）+ React/TS 前端（web/）

1. 设计原则

  • Go-only：所有改动落在 internal/ 与 web/，不触碰 api/、rag/ 等 Python 遗留目录。
  • 复用现有 seam：优先扩展已有的 internal/permission、internal/admin、迁移机制与管理前端，不另起炉灶。
  • 默认拒绝：知识库可见性从"默认可见 / team 共享"切换为"显式授权才可见"，一次性切换，不做双轨兼容开关（本仓库为二次开发自有产品基线）。
  • 校验在服务端：前端按钮级隐藏只是展示层优化，所有权限判定以服务端为准，API 层同样强制校验。

3. 数据模型设计

全部为新增表 / 新增列，不修改既有列语义。GORM 模型放 internal/entity/，遵循现有命名与索引约定（Go 侧索引名 idx_<table>_<column>；唯一约束用命名 uniqueIndex:，不用裸 unique——避免 namedIndexMigrator 幻影删除问题）。

3.1 组织与角色

-- 部门 / 子公司（树形）
department(
  id          bigint PK,
  name        varchar(64)  NOT NULL,
  parent_id   bigint       NOT NULL DEFAULT 0,   -- 0 = 根
  path        varchar(512) NOT NULL DEFAULT '',   -- 物化路径 /1/5/12/，用于子树筛选
  create_time datetime, update_time datetime,
  INDEX idx_department_parent (parent_id)
)

-- 角色（超管自定义；无内置行，超管不走 role 体系）
role(id, name varchar(64), description varchar(255),
     create_time, update_time, UNIQUE uni_role_name (name))

-- 功能权限点（按钮级，代码内置 seed，启动时 upsert）
function_permission(
  code  varchar(64) PK,      -- 如 kb.create / doc.upload / chat.create / agent.create
  name  varchar(64), description varchar(255)
)

-- 角色-权限点关联
role_permission(role_id bigint, permission_code varchar(64),
  PRIMARY KEY (role_id, permission_code))
权限点 code（初始清单，实施时与功能菜单逐一对齐）语义
kb.create创建知识库（P0）
kb.view / doc.upload / doc.delete / doc.reparse知识库与文档操作粒度示例
chat.create / agent.create / file.manage其他功能域，按现有菜单逐项确认后注册

3.2 用户扩展

ALTER TABLE user ADD COLUMN department_id bigint NOT NULL DEFAULT 0;  -- 0 = 未分配
ALTER TABLE user ADD COLUMN role_id      bigint NOT NULL DEFAULT 0;   -- 0 = 无角色（无功能权限）
INDEX idx_user_department (department_id), INDEX idx_user_role (role_id)
决策 D1：一个用户一个角色（PRD 已确认），故用列而非关联表；角色删除前校验 user.role_id 引用（阻断式）。

3.3 知识库成员授权

-- 知识库成员：permission ∈ {view, edit}；所有者与超管不入本表
kb_member(
  id bigint PK, kb_id bigint NOT NULL, user_id bigint NOT NULL,
  permission varchar(8) NOT NULL,           -- 'view' | 'edit'
  create_time datetime,
  UNIQUE uni_kb_member (kb_id, user_id),    -- 一人一库一种权限（升级=改行）
  INDEX idx_kb_member_user (user_id)        -- "我可见的知识库"反查
)

知识库可见性判定（所有 KB/文档查询的统一前置条件，唯一实现点 internal/permission/kb_access.go）：

可见 ⇔ user.is_superuser = 1
    OR knowledgebase.user_id = user.id          -- 所有者
    OR EXISTS (SELECT 1 FROM kb_member m
               WHERE m.kb_id = kb.id AND m.user_id = user.id)
决策 D2：部门归属不冗余进 knowledgebase，超管按部门筛选知识库通过 JOIN user 实现；决策 D3：可见性切换后，存量知识库除所有者与超管外一律不可见（breaking change，符合 PRD 默认拒绝原则）。原 knowledgebase.permission（me/team）字段保留存储但企业链路不再用它做跨用户放行。

3.4 知识库目录

kb_folder(
  id bigint PK, kb_id bigint NOT NULL,
  parent_id bigint NOT NULL DEFAULT 0,        -- 0 = 根（未分类）
  name varchar(128) NOT NULL,
  path varchar(1024) NOT NULL DEFAULT '',     -- 物化路径，面包屑与子树校验用
  create_time datetime, update_time datetime,
  UNIQUE uni_kb_folder (kb_id, parent_id, name),  -- 同父级不重名
  INDEX idx_kb_folder_parent (kb_id, parent_id)   -- 懒加载查询
)
ALTER TABLE document ADD COLUMN folder_id bigint NOT NULL DEFAULT 0;  -- 0 = 根目录
INDEX idx_document_folder (kb_id, folder_id)

规模设计：目录树接口按 parent_id 逐层懒加载；文档列表按 (kb_id, folder_id) 过滤 + 分页（复用现有文档分页模式）；库内全文搜索走现有 ES/Infinity 检索链路，命中结果回查 folder_id → folder.path 拼目录路径展示。同一父目录重名由唯一索引兜底，应用层先查后插并给出友好错误。

4. 服务端权限校验设计

4.1 两级校验

层级判定依据实现
功能权限（按钮级） user.role_id → role_permission 集合 登录 / 会话建立时将 permissions []string 写入认证上下文；新增 internal/permission/feature.go 提供 RequireFeature(c, "kb.create") gin 校验 helper，供功能端点挂载。
资源权限（知识库级） 3.3 可见性判定 + kb_member.permission internal/permission/kb_access.go 提供 RequireKB(c, kbID, level)（level ∈ view/edit/owner），从路由参数取 kb_id，先查知识库存在性（不存在与无权限统一返回"不存在或无权限"，防探测），再按矩阵放行。文档操作端点先取 document.kb_id 再走同一入口。

4.2 关键流程

  • 知识库列表：DAO 层列表查询统一带可见性条件（3.3 的 OR 组合），一次 SQL 完成，不做内存过滤——上万知识库也不退化。
  • 删除账号前置校验：DELETE /api/v1/admin/users/:username 增加检查 knowledgebase.user_id = 该用户 计数，非零返回明确错误（列出待转移知识库数量），前端引导先转移。
  • 强制转移所有权：事务内更新 knowledgebase.user_id/tenant_id → 若原所有者不在成员表则插入 kb_member(permission='view') → 若新所有者残留在 kb_member 则删除该行。失败整体回滚。
  • 批量按部门添加成员：接口入参 {kb_id, permission, user_ids[], department_ids[]}，服务端展开部门成员后逐人 upsert kb_member（单事务），返回成功/跳过（已存在同权限）明细。

5. API 设计

5.1 管理端（/api/v1/admin，挂 AuthMiddleware + 仅超管可访问）

分组端点说明
组织架构GET/POST /departments、PUT/DELETE /departments/:id树形 CRUD；删除时校验无子部门、无用户、无归属知识库
GET /departments/:id/users部门成员列表
GET /departments/tree整树（缓存于内存，变更失效）
用户既有 users 端点扩展创建/编辑增加 department_id、role_id 字段；删除增加"名下有知识库"前置校验
GET /users/:username/kb-ownership名下知识库清单（转移引导）
角色GET/POST /roles、PUT/DELETE /roles/:id角色 CRUD；删除校验无用户引用
GET /permissions功能权限点全量清单（前端勾选树数据源）
GET/PUT /roles/:id/permissions读取/整体保存角色权限点集合
超管知识库GET /kb-admin、PUT /kb-admin/:id/members、PUT /kb-admin/:id/owner全量知识库（按部门/所有者筛选）、改成员、强制转移所有权（二次确认由前端承担）

5.2 用户端（/api/v1，挂现有认证中间件）

分组端点说明
我的权限GET /user/permissions返回 { department, role, permissions[] }（按钮级 code 列表），前端登录后拉取
成员授权GET/PUT/DELETE /kb/:id/members、POST /kb/:id/members/batch仅 owner / 超管（RequireKB owner）；batch 支持部门整批
可选授权人GET /users/search?q=、GET /departments/brief成员选择器数据源（返回全量用户摘要，供搜索）
目录GET /kb/:id/folders?parent_id=懒加载子层；带 keywords 时全库目录搜索
POST/PUT/DELETE /kb/:id/folders(/:fid)、PUT /kb/:id/folders/:fid/move目录 CRUD 与移动；删除校验非空（递归含子目录与文档）
文档端点扩展列表/上传增加 folder_id 参数与字段；POST /kb/:id/documents/move 批量移动文档到目标目录

6. 数据迁移方案

  • 在 internal/dao/migration.go 注册一个新版本门控迁移步骤：建 department / role / function_permission / role_permission / kb_member / kb_folder 六表 + user 两列 + document.folder_id 列；function_permission 以代码内置清单 seed upsert。
  • 同步更新 docs/administrator/upgrade_and_migration/database_change_log.md：新增版本常量、InitDB 启动顺序表与"Version overview"表格行。
  • 存量数据默认值：department_id=0（未分配，超管后续指派）、role_id=0（无功能权限，超管指派）、folder_id=0（根目录）、kb_member 为空（仅所有者可见）。
  • 唯一内置超管：沿用现有 is_superuser 初始化逻辑（cmd/ragflow_server.go 的 superuser 初始化），补充约束：管理端"授权管理员"接口改为仅当目标已是唯一超管时的降级保护——全系统最多一个 is_superuser=1，降级唯一超管的请求拒绝。
风险提示：可见性切换是 breaking change——升级后非所有者用户将看不到原本可见的知识库。发布说明中需明确告知：请超管先通过批量授权完成存量知识库的成员分配。

7. 前端设计

7.1 按钮级权限控制

  • 新增 src/hooks/use-permission.ts：基于 TanStack Query 拉取 /user/permissions，Zustand 缓存（登录会话生命周期）；提供 hasPermission('kb.create')。
  • 新增 src/components/permission-gate.tsx：声明式包裹按钮/操作区，无权限时不渲染（<PermissionGate code="doc.upload"></PermissionGate>），接入点示例：知识库创建按钮、[dataset-action-cell.tsx](file:///f:/trae_project/ragflow/web/src/pages/dataset/dataset/dataset-action-cell.tsx) 的文档操作按钮组、上传入口。
  • 权限点 code 与后端 function_permission.code 共用同一枚举定义（前端常量文件 + 后端 seed 同名，评审时逐一对齐）。
  • 服务端 403 响应统一提示，不做静默失败。

7.2 目录树 UI

  • 知识库详情页改造为左侧目录树 + 右侧文档列表：树组件懒加载（展开时拉子层），右键/工具条提供新建、重命名、移动、删除（删除带非空校验提示 + 二次确认）；文档列表随选中目录过滤分页，上传弹窗默认选中当前目录。
  • 目录树遵循 web/AGENTS.md：shadcn/ui 组件、query key factory（DatasetKeys 家族扩展）、三层请求分层（hooks → services → next-request）、i18n 只加 zh/en。

7.3 管理端页面（web/src/pages/admin/）

  • 新增组织架构页（部门树 CRUD + 成员查看）；用户页表单增加部门/角色字段与"名下知识库转移"引导；角色页对接第 5.1 真实端点（现有 roles.tsx 骨架 + role-form.tsx 表单复用）；新增知识库管理页（全量列表、按部门/所有者筛选、成员编辑弹窗、强制转移所有权对话框）。
  • 知识库前台页新增成员管理弹窗（owner 可见）：人员搜索选择器 + 部门整批导入 + 查看/编辑名单维护。

10. 待评审确认点

D1　用户-角色用单列（一人一角色）而非关联表，是否符合长期规划？
D2　知识库归属部门不冗余存储、实时 join 推导；若未来部门筛选成为高频重查询，再引入冗余列。
D3　可见性切换为 breaking change（存量知识库升级后仅所有者与超管可见），不做兼容开关。
D4　ee-stub 权限 seam 保持不动，按钮级权限走独立新模块；若未来要对齐上游 EE 形态再收敛。
